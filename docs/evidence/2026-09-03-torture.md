# Torture test — attacking the finished solution

**Date:** 2026-09-03 · **Context:** Steps 1–9 complete and live-proven; this session
deliberately attacked the result before final documentation. Standing rule for the
phase: *not every sharp edge requires a solution* — a fix had to be small and clearly
right, or the edge is documented and left sharp.

Four instruments: live probes against the real platform, an adversarial design
review, a cold-read of the documentation as a stranger would follow it, and an
alignment audit against Microsoft's published CI/CD guidance.

## Live probes

| Probe | What was done | Result |
|---|---|---|
| T1 — pause during deploy | Capacity paused while both solutions' dev deploys were in flight | Both failed ugly: sales hit fabric-cicd's retry ceiling ("Maximum execution duration (300 seconds) exceeded after 376.2s"), finance a raw `CapacityNotActive` on a PATCH. The race is real → **fixed**: the pause action now defers while build/promote/prod-schedule runs are in progress, and fails unless the final state is Paused |
| T1b — paused from the start | Build dispatched with the capacity already Paused | Same raw errors — `deploy.py`'s capacity preflight never fired. Probe: the Fabric API truthfully reports `Inactive` when ARM says `Paused`, so the cause is visibility — `GET /capacities` as a deploy identity does not return a capacity it holds no permission on, and the guard skipped silently. **Fixed only to be honest**: the invisible case now prints a note; the real protections are the quickstart's resume-first instruction and the pause deferral above. Granting deploy identities capacity permissions just to improve an error message would be the wrong trade |
| T2a — promote a failed run | `promote` dispatched with a red build's run ID | Clean refusal: "concluded 'failure' — only green dev-proven builds promote" |
| T2b — promote a bogus run ID | Non-existent run ID | Refused via a raw HTTP 404 — safe, less polite. Inputs are now regex-validated first; a well-formed-but-wrong ID still 404s. Accepted |
| T5 — guard fuzzing | Hostile solution trees: traversal in displayName, weird folder names, symlinks, empty folders, oversized files | Traversal caught by the folder-match guard. Weird solution names raised no guard violation → enforcement placed at the single derivation point instead: the workflow matrix filter (`[a-z][a-z0-9-]+`, matching Terraform's rule). Symlinks accepted silently — **left sharp**: PR review and push protection are the fence, and `tarfile` stores links rather than following them. An empty solution folder deploys nothing but creates workspaces — that is simply what a new solution looks like |

## Adversarial review

Twelve findings (3 high / 5 medium / 4 low), each verified against file and line. The
high findings compounded into one chain: a zero-approval merge to `main` could reach
an **ungated** platform identity — the reviewer-gated `platform` environment existed,
but no workflow used it — and `promote` would accept any green run of any workflow as
provenance. Two small changes cut the chain.

| Finding | Disposition |
|---|---|
| `platform-terraform` ran without the `platform` environment gate | **Fixed** — one line; every plan and apply now waits for the reviewer |
| `promote` accepted any successful run as a bundle source | **Fixed** — provenance now asserts the run is `build.yml` on `main`, and inputs are validated |
| Deleting a solution folder + one gated apply destroys prod workspaces | **Accepted** — the reviewer-gated apply is the control, plus 30-day workspace retention; `prevent_destroy` was rejected earlier because it obstructs legitimate retirement. Recorded in the divergences table (single-state trade-off) |
| Dispatch inputs interpolated into shell | **Fixed** — env-var passing + regex validation |
| Capacity pause races in-flight deploys | **Fixed** (T1) |
| `prod-schedule` could overlap a promote to prod | **Fixed** — shares the `deploy-<solution>-prod` concurrency group |
| Unpinned `setup-uv` tool version | **Fixed** — pinned everywhere |
| Solution names flow unvalidated into the matrix | **Fixed** (T5 filter) |
| Repository-admin ruleset bypass | **Accepted** — documented solo-maintainer trade-off; drop before v1 |
| Platform identity holds `Group.ReadWrite.All` | **Accepted** — it manages viewer-group membership; the scope is tenant-wide because Graph offers nothing narrower for this |
| Rollback depends on 90-day artifact retention and tool pins | **Documented** in the promotion evidence |
| Pause failures were swallowed (`exit 0` regardless) | **Fixed** (T1) |

## Cold read of the documentation

A reviewer followed the quickstart as a stranger with a fresh tenant. The findings
were almost all documentation debt, now paid: the new-solution provisioning sequence
(merge → gated apply → re-run setup script → re-run build) was undocumented and the
first build after a merge *always* fails; the platform Terraform variables were
written where no workflow could read them (now repo-level, and the setup script now
writes all thirteen rather than eight); prerequisites lacked the Entra rights; fork
notes (disabled workflows, schedule activation, the finance example's hardcoded
workspace IDs) were absent; the README claimed five steps, weather data, and a
two-solution tree that showed one. Two latent code bugs surfaced the same way:
`operate.py` crashed on any solution without a dbt project, and `prod-schedule`
hardcoded `sales` — both fixed, so the heartbeat now derives its matrix from the tree
like every other workflow and the fiftieth-solution claim is mechanically true.

## Alignment with Microsoft's guidance

Audited against the
[best-practices page](https://learn.microsoft.com/fabric/fundamentals/understand-best-practices-fabric-cicd)
and the March 2026 CI/CD announcement. Verdict: the repository lands on the
recommended end state (API-driven release, fabric-cicd config-based deployment,
Terraform infrastructure, service principals, trunk-based branching) and exceeds it
on secrets and build provenance. Three decisions had been taken silently against
Microsoft's explicit framing — shared capacity, single Terraform state, no
Git-connected workspaces — plus one genuine code gap (unpaginated, throttle-naive
REST calls, which the guidance warns about directly). The gap is fixed; the
decisions are now argued in
[the divergences section](../path-to-production.md#where-this-design-diverges-from-microsofts-guidance),
with the terminology mapping (solution ↔ *Fabric CI/CD project*, promote ↔ *release
process*, bundle as this repository's own extension). The announced Bulk
Import/Export APIs joined the watch-list.

## Corrected beliefs

- "`deploy.py` preflights the capacity state" — not for deploy identities: the
  capacity is invisible to them, and the check skipped silently (T1b).
- T1's first reading ("the preflight message was unclear") was wrong — the pause had
  landed mid-deploy, so the preflight never ran at all. The clean-exit path exists
  but no CI identity can reach it.
