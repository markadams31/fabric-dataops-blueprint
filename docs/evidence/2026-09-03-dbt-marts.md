# Step 5 — a real solution: Bronze seed → dbt marts, green first try

**Date** 2026-09-03 · **Run** build 33688704350 (success, first attempt)

## What was proven

- **The full data path works as the deploy identity**: after the fabric-cicd
  publish, the deploy job uploaded the committed retail samples into
  `lh_bronze/Files/retail/` over the OneLake DFS API, then ran `dbt build` against
  `wh_analytics` — staging tables reading Bronze via `OPENROWSET`, marts
  (`dim_customers`, `fct_orders` incremental-merge) on top. **17/17 PASS**
  (5 models, 12 tests), roughly 40 s of dbt time.
- **The last trial→MI doubts are closed**: OneLake write with an MI token, and
  T-SQL/OPENROWSET through dbt-fabric's CLI auth after a tenant-level login. With
  fabric-cicd (Step 4) and workspace creation (S27), every identity claim in the
  architecture is now proven under managed identities with zero secrets.
- The warehouse SQL endpoint is discovered at deploy time from the Fabric API
  (`connectionString`), exported as env vars into a committed, secret-free
  `profiles.yml` — nothing environment-specific lives in the dbt project.

## Shape notes

- Staging models materialise as tables (one OPENROWSET scan per run) with explicit
  casts; identifiers all lowercase for the case-sensitive BIN2 collation (prior
  evidence E31). `generate_schema_name` uses custom schemas verbatim → `silver`
  and `gold`.
- Sample data is deterministic (`samples/generate.py`, seed 42) and committed, so
  forks need no generation step and every deploy seeds identical bytes.
- Trimmed from this step deliberately: the weather source (arrives with the
  report), and a Spark ingestion notebook (the seed upload plays ingestion for the
  demo; a scheduled notebook path lands with prod-schedule).
